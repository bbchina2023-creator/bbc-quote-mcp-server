### DEV-016.50 structured multi-item writeback

A live audit of the current reference deal proved a writeback defect that intake-only recovery did not solve. The current source documents contain two active item rows, but canonical `Товары` contained one aggregate partner row with batch value `46485.8`, blank item name/article/quantity, and `PARTNER_TOTAL` semantics. This meant the intake layer could understand two source items while the deterministic calculation layer could still read only one stale canonical aggregate.

`4.1.50` closes that gap:

1. The direct-chat writeback recognizes structured current-deal export tables by their actual bilingual headers instead of relying only on the older `Заказ` layout.
2. Only active source rows with a meaningful name, quantity greater than zero and invoice amount greater than zero become canonical items; zero/template rows are excluded.
3. Item-level source fields are preserved: name, article, quantity, production time, supplier price fields, China VAT fields, China domestic logistics, invoice amount and source lineage.
4. Item-detail sheets enrich the canonical rows with packages, gross weight and volume.
5. A unique current-deal partner customs profile enriches both items with source-proven TN VED, percentage duty method/rate and import VAT rate. Ambiguous profiles remain unresolved rather than guessed.
6. When structured multi-item evidence exists, `bbcChatApiApplyDealAndItems_()` writes those item rows first and skips the aggregate scalar item fallback.
7. The deterministic item IDs remain stable by deal and item number, so the old aggregate position-1 row is replaced by current item 1; stale imported positions outside the current item set are downgraded for audit rather than used by calculation.
8. Current reference source reconciliation is explicit: item quantities `220 + 1780 = 2000`; item invoice amounts `4093 + 42392.8 = 46485.8`.
